## Аудит коду та різних екранів

- За запитом перевірено 10 роздільностей від 320×568 до 1920×1080, у тому числі
  планшети й горизонтальні телефони: 280 станів, фінально без переповнень і JS-помилок.
- Виправлено перекриття «Назад»/заголовків, сітку залишків на 320 px, компактність
  камери в landscape та обрізану підказку. Масштабування сторінок більше не заборонено.
- Знайдено й усунено гонку таймерів фокуса: швидкий Enter міг потрапити в попередній
  крок і зірвати збереження. Фокус робочих кроків тепер установлюється одразу.
- Імена, примітки, локації та OCR-текст в адмінці/Lider виводяться без виконання HTML;
  небезпечні вставки імен у onclick замінені обробниками. Додано перевірку некоректного
  JSON/значень, дати/типів завдання, відсутнього контейнера. HTML при втраті сесії
  спрямовує на вхід, API зберігає 401/403.
- Старі PUT/DELETE ICC для sort_id-записів заблоковано: редактор веде у «Рухи та
  залишки» через openInventoryJob. Зняті з роботи deleted-завдання не показують
  свої ICC у списку роботи. Непов’язану історію можна редагувати з валідацією чисел.
- Undo перевіряє також цілісність історичної проєкції, при проблемі відкочується.
  «Один товар» не починає рух або Undo, якщо pending не вдалося зберегти у браузері.
  Вибір нової роботи прибирає стару чернетку лише якщо вона БЕЗ pending;
  непідтверджений запит спочатку потрібно повторити.
- Старий Lider тепер створює правильні Single/Mix завдання; вкладки й OCR-фільтр
  працюють без глобального event. Роль лідера не додавалася — це той самий admin.
- Підсумок і межі перевірок: `artifacts/audit-2026-10-31/REPORT.md`, матриця final.json,
  скрипти responsive.mjs / behavior.mjs. Пройшли 92 Python-тести, 36 JS-тестів,
  повний браузерний сценарій на 320×568, 768×1024, 1366×768, 844×390.
- Реальна база перевірена тільки читанням: integrity_check=ok, немає від’ємних
  залишків, змішування контекстів або незбалансованих перенесень. Тести — на тимчасових
  базах. Схема для цих виправлень не змінювалася, реальні фото не редагувалися.
  Перед оновленням сервера також створено backup
  `backup_initial/warehouse_before_audit_fixes_20261101_002341.db`.

  Pre-sort сканувань і старих SORT-палет тільки з достовірним sort_id.

## Що хоче користувач

Під час розвантаження погано відсортованого контейнера працівник сканує кожен
картон, кладе його на змішану пронумеровану палету, закриває повну палету
та починає наступну. Дані потрібно зберігати для подальшого сортування.

Початковий приклад товару: `4567 / JP-A / 30 PACK`. Один товар може бути на
палетах №1, 4, 10, 12, 16, 23. Збережений облік дозволяє визначити ці палети.
Однак за пізнішою прямою вказівкою користувача пошук «Де лежить товар?»
прибрано саме з робочого інтерфейсу Pre-sort. Не повертай його туди без запиту.

## Поточні домовленості та реалізація Pre-sort

1. Створити Pre-sort може лише адміністратор. Це перевіряється сервером,
   а не тільки прихованою кнопкою.
2. Створення: адмінпанель → «Сортування» → «Створити сорт» → режим PRE-SORT.
   Форма спільна із SORT: зона/рампа, типи Single/Mix/Vevor, дата, примітки.
3. На головній сторінці є ДВІ окремі кнопки: SORT та PRE-SORT.
   Це остання домовленість; раніше Pre-sort показувався у спільному списку SORT.
4. SORT показує звичайні сорти (`/api/sorts?mode=sort`). PRE-SORT відкриває
   вибір уже створених адміністратором Pre-sort. Працівник не створює нове завдання.
5. Кожен працівник може відкрити одну власну палету в межах Pre-sort.
   Нумерація спільна для працівників, окрема для кожного Pre-sort.
6. Один фізичний картон = одне сканування = додавання однієї одиниці.
   `30 PACK` — характеристика наклейки, а не кількість, що додається за сканування.
7. Товар розрізняється за типом, кодом, локацією та PACK. Для Mix — повний ICC,
   без обов'язкових полів локації/PACK. Однакові 4 цифри не завжди означають той самий товар.
8. Камера має такий самий вигляд, як у Single/Mix: відео, рамка для наклейки,
   «Зробити фото», спалах за підтримки телефону. Це браузерна камера,
   а не системний вибір файлу чи фотографії.
9. Повне розпізнавання автоматично зберігає 1 картон. Неповні дані можна
   виправити вручну та зберегти. Кнопка називається «Додати», НЕ «Додати 1 картон».
10. Після підтвердження збереження з'являється зелене повідомлення
    «✓ Картон додано» по центру екрана приблизно на 2 секунди.
11. Після успішного додавання вікно камери ЗАЛИШАЄТЬСЯ ВІДКРИТИМ.
    Можна одразу сфотографувати наступну наклейку. Автоматично повторно
    фотографувати чи повторно рахувати той самий кадр не потрібно.
    Камера закривається вручну через ✕ / Escape; потік при цьому зупиняється.
12. Є скасування останнього картону на своїй відкритій палеті та закриття палети.
    На сторінці залишилися кількість картонів і список палет, без пошуку товарів.
13. Повторення того самого HTTP-запиту не додає другий картон: використовується
    `request_id`. Непідтверджений запит зберігається в sessionStorage для повторення.
14. Додавати можна тільки дозволені адміністратором типи наклейок.
    Закритий/призупинений Pre-sort доступний для перегляду, але не для додавання.
    Pre-sort із палетами не видаляється через адмін API; його можна закрити.
15. Адмін може закрити весь Pre-sort на його сторінці або в адмінпанелі.
    Це атомарно закриває також усі його відкриті палети. Закриті Pre-sort
    залишаються видимими в адмінпанелі для подальшого переведення.
16. Адмін може натиснути «Перевести в SORT» лише для закритого Pre-sort.
    Завдання зберігає ID, назву, налаштування й зв'язок із джерельними палетами,
    змінює mode на sort, status на active. Початкові сканування не змінюються.
    Повторення запиту не створює дубль. Звичайний користувач не може переводити.
17. У переведеному SORT блок «Палети з Pre-sort» шукає товар за введеними
    чи відсканованими даними. Однакові коди з іншими PACK/локацією не змішуються.
    Для Mix використовується повний код. Дані іншого завдання не показуються.
    Кількість позначена як зібрана на момент завершення Pre-sort — не поточний залишок.
18. Переведення не зараховує розвантаження як виконане сортування. Видалення
    завдання з початковими палетами заблоковано також після переведення.
19. Користувачу пояснено етап показу палет: у переведеному SORT, після вибору
    типу товару, при введенні коду/локації/PACK або заповненні полів результатом
    сканування. Блок «Палети з Pre-sort» видно ще ДО натискання «Продовжити».
    Після введення лише коду можливі кілька варіантів; локація й PACK уточнюють збіг.
20. 2026-10-24 додано окрему вкладку адмінпанелі «Pre-sort: картони».
    Адмін обирає будь-яке джерельне завдання: активний/закритий/призупинений
    Pre-sort або переведений SORT, зокрема вже закритий SORT. Є журнал по одному
    запису на картон: час, тип, ICC, локація, PACK, палета, працівник, стан запису.
    За замовчуванням видно додані картони; скасовані можна включити окремим фільтром.
    Є пошук за кодом/локацією/PACK/номером палети/працівником, фільтр типу,
    підсумки палет/картонів/скасувань і сторінки по 100 записів.
    На картках Pre-sort в адмінпанелі є кнопка «Переглянути картони».
    Перегляд тільки для admin, без редагування реальних сканувань та без змін схеми.
21. У цій вкладці основний вигляд тепер «Список товарів», а окремі записи доступні
    перемикачем «Журнал додавань». Товар об'єднується за типом + ICC + локацією + PACK.
    Приклад рядка: «3245 GZ-A 40 PACK», додано «12 із 40», залишилось 28,
    прогрес 30%, 3 палети, номери та кількість на кожній, кількість закритих палет,
    час останнього додавання. Скасовані записи в цих підрахунках не враховуються.
    Mix має кількість без плану. Перевищення PACK явно показується без обрізання
    фактичного числа картонів. Агрегація виконується за всім завданням, а не лише
    поточною сторінкою журналу. Пагінація списку товарів — по 100 товарів.
    Пошук у списку — код/локація/PACK; пошук палет/працівників лишився в журналі.
    Це підсумки Pre-sort, зокрема після конвертації; фізичний відбір не списується.

## Огляд логіки та зрозумілості програми (2026-10-25)

Користувач дозволив покращити інтерфейс і виправити підтверджені баги.
Підсумок та відкладені ідеї також у `IMPROVEMENTS.md`.

- Виправлено критичний баг SORT: раніше check розрізняв наклейки точно,
  а add/close знаходили товар лише за цифрами та типом, без sort_id/PACK/букв.
  Новий `sorting.py` виконує роботу лише в обраному завданні й за повною наклейкою.
- Нові API: POST `/api/sort/check`, `/api/sort/submit`, `/api/sort/pallet/close`.
  Submit приймає sort_id,type,icc_code,total_cartons,location_code,cartons_count,
  pallet_number,force_new,request_id. Запис ICC, палети, лічильників, статистики,
  журналу й підтвердження запиту атомарний (`BEGIN IMMEDIATE`).
- Нові записи ICC мають sort_id. Старі записи без sort_id не прив'язувалися
  навмання, не видалялися, їхні старі лічильники не перераховувалися.
- `sort_operations` зберігає payload/відповідь успішного запиту. Той самий UUID
  з тим самим payload не додає дубль; інший payload/user з цим UUID відхиляється.
  Додавання на неактивний SORT, не дозволений тип, від'ємні/дробові кількості
  та перевищення PACK для Single/Vevor блокуються. Mix — без PACK-ліміту.
- Непідтверджений SORT payload зберігається в sessionStorage окремо за userId.
  Є «Повторити збереження». Поки операція непідтверджена, іншу не починають.
  Мережева помилка/5xx/401 зберігає pending; 400/409 дозволяє виправити дані.
- Close вимагає sort_id,icc_id,pallet_id. Повторне закриття старої палети
  не закриє наступну. Можна закрити власну палету завершеного ICC/завдання на паузі.
  Закриття SORT адміністратором атомарно закриває всі його відкриті палети.
  Видалення завдань зі збереженим обліком заблоковане; їх можна закрити.
- Небезпечні старі write-API без task scope відхиляються з вимогою оновити сторінку.
  Legacy check/add/close з повними новими даними делегують новим handlers;
  окремий legacy create ICC відхиляється — створення тепер частина submit.
- Перед міграцією створено `backup_initial/warehouse_before_sort_atomic*.db`.
  Перед деплоєм зроблено ще свіжу копію. Після запуску перевірено: кількість
  історичних записів users/sorts/ICC/палет/Pre-sort не змінилася, нова таблиця є.
- Vevor має форму й камеру як Single; доступні лише типи обраного завдання.
  Відновлюється збережений активний SORT; видно ID завдання та джерело Pre-sort.
  Під основними окремими кнопками пояснено різницю SORT і Pre-sort; робота має 3 кроки.
- Порожнє джерело Pre-sort більше не приховане. API повертає has_source/source_name.

  видно в основній формі, на кроках кількості та цільової палети, а після додавання

- У завершеної партії можна закрити останню палету і явно почати нову партію.
- В адмінці усунено дубль showSortSubtab, працюють «Завершені товари» та реєстр палет
